# CHANGELOG — SQL backup restore clone (`sqlbrc`)

История изменений сервиса `sqlbrc`. Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
нумерация версий — [SemVer](https://semver.org/lang/ru/); схема тегов (`sqlbrc-vX.Y.Z`) и порядок релиза —
в корневом [CONTRIBUTING.md](../CONTRIBUTING.md). Указатель по всем инструментам — [../CHANGELOG.md](../CHANGELOG.md).

## [Unreleased]

Веб-интерфейс и API: команда `serve` с теми же операциями, что и в CLI.

### Add

- команда `sqlbrc serve [--listen адрес]` — веб-интерфейс и API поверх тех же операций:
  бэкап, восстановление, клонирование и уборка запускаются формой на странице или запросом
  к API, а ход работы виден в журнале задач;
- `internal/auth`: вход по bcrypt-хэшам из `auth.users`, сессии в памяти с временем жизни
  `auth.session_ttl`, ограничение неудачных попыток входа (`auth.login_backoff`,
  `auth.max_login_attempts`), токены API из `auth.token_file` в формате `<логин>:<токен>`;
- `internal/web`: страницы «Базы и бэкапы» и «Журнал задач», форма входа; защита от подделки
  запросов (CSRF-токен сессии в каждой форме), cookie сессии `HttpOnly` + `SameSite=Strict`,
  заголовки безопасности, предел размера запроса `server.max_body_bytes`;
- API `/api/v1`: `GET /backups`, `GET /jobs`, `POST /backup`, `POST /restore`, `POST /clone`,
  `POST /prune` — доступ по токену (`Authorization: Bearer …`), ответы в JSON, а отказ операции
  отличается от сбоя (`rejected`/`conflict` против `internal`);
- `GET /healthz` — проверка живости сервиса для systemd и мониторинга (без аутентификации);
- `sqlbrc backup --all` — бэкапы всех обслуживаемых баз кластера: команда для расписания,
  которому список баз заранее неизвестен; отказ по правилам и сбой считаются отдельно;
- режим `postgres.mode: tcp` — подключение по сети от имени роли с паролем из файла
  (`postgres.password_file`, PGPASSFILE): так работает поставка в контейнере, где нет
  локального сокета и peer-аутентификации; `doctor` проверяет файл пароля (права 0600);
- поставка:
  - `Dockerfile` — образ на alpine с утилитами PostgreSQL 15, непривилегированный пользователь
    `sqlbrc`, `HEALTHCHECK` через `/healthz`; точка входа создаёт файл пароля с правами 0600
    из переменной `SQLBRC_PGPASS`;
  - `deploy/compose.example.yaml`, `deploy/config.container.example.yaml`, `deploy/.env.example` —
    стенд «PostgreSQL 15 + сервис» для проверки поставки;
  - `deploy/systemd/sqlbrc.service`, `deploy/systemd/sqlbrc-backup.{service,timer}` — служба
    с ограничениями (ProtectSystem, ReadWritePaths) и ежедневное расписание бэкапов;
  - `deploy/nftables/sqlbrc.nft` и `deploy/cron.d/sqlbrc` — ограничение доступа к интерфейсу
    и расписание для систем без systemd.

### Исправлено

- `SQLListDatabases` обращался к колонке `pg_database.dbtablespace`, которой в PostgreSQL нет
  (нужна `dattablespace`): `sqlbrc backup --all` и проверки, читающие список баз, падали
  на `ERROR: column d.dbtablespace does not exist`. Ошибка найдена прогоном поставки
  в контейнере на живом PostgreSQL 15.

## [0.2.0] - 2026-09-21

Операции с базами и каталог бэкапов: команды `backup`, `restore`, `clone`, `backups`
и `jobs`, очередь задач с ограничением параллелизма, журнал задач в файле и команда
создания bcrypt-хэша пароля.

### Add

- команды CLI:
  - `backup --db <имя> [--tag] [--note]` — дамп базы в каталог сервиса, после успешного
    снятия применяется политика хранения;
  - `restore --db <имя> [--backup <идентификатор>] [--no-clean]` — разворот базы из бэкапа
    (по умолчанию последнего): отсутствующая база создаётся, существующая очищается,
    активные подключения завершаются;
  - `clone --from <источник> --to <стенд>` — стенд из бэкапа другой базы; локаль стенда
    берётся у источника, существующий приёмник не перезаписывается;
  - `backups list [--db]` и `backups prune [--db] [--dry-run]` — список бэкапов и уборка
    по политике хранения с проверкой плана «на бумаге»;
  - `jobs [--limit] [--json]` — журнал задач: вид операции, база, состояние, время, итог;
  - `hash-password --login <имя>` — bcrypt-хэш пароля для `auth.users`; пароль читается
    из stdin, а не из аргументов командной строки;
- коды возврата: `0` — успех, `1` — ошибка, `2` — операция отвергнута до начала
  (чужая или защищённая база, `server.read_only`, не хватает свободного места);
- `internal/store`: каталог бэкапов `<storage.dir>/<база>/<метка времени>[-<метка>].dump`
  с файлом метаданных рядом (размер, sha256, формат, сжатие, версия сервера, размер базы,
  задача журнала), запись через `.part` с переименованием, поиск и список бэкапов,
  проверка свободного места и политика хранения (чистая функция `store.Plan`),
  уборка незавершённых записей;
- `internal/jobs`: очередь задач с ограничениями `jobs.max_parallel` и `jobs.max_per_db`
  и журнал задач в формате JSONL (`<storage.state_dir>/jobs.jsonl`, права 0600) с обрезкой
  до `jobs.retain` записей; повреждённая строка журнала не ломает остальные;
- `internal/backup`: операции сервиса поверх хранилища, очереди и `pg`: служебный бэкап
  с меткой `pre-restore` перед восстановлением, проверка контрольной суммы архива до
  первой команды, меняющей базу, создание базы с локалью образца, завершение подключений,
  `pg_restore --clean --if-exists`;
- `internal/pg`: сборка служебных запросов с проверкой имён (`QuoteIdentifier`,
  `QuoteLiteral`), операции с базами (`DatabaseExists`, `DatabaseLocale`, `DatabaseSize`,
  `Sessions`, `TerminateBackends`, `CreateDatabase`, `DropDatabase`, `AlterDatabaseOwner`),
  дамп и восстановление (`Dump`, `Restore`, `ArchiveSummary`) и ожидание готовности
  сервера (`WaitForReady`);
- `internal/passwd`: создание и проверка bcrypt-хэшей паролей (ограничения длины:
  bcrypt учитывает только первые 72 байта);
- fuzz-цели на разбор имени файла бэкапа (`FuzzParseArchiveName`) и строки журнала
  задач (`FuzzParseJobLine`);
- новые зависимости: `golang.org/x/crypto` (bcrypt);
- CI и релиз сервиса: `codeql.yml` анализирует модуль `sqlbrc` отдельной категорией отчётов,
  `trivy-scan.yml` проверяет его файловую систему теми же «воротами» (CRITICAL/HIGH роняют прогон),
  `release.yml` собирает бинари по тегу `sqlbrc-vX.Y.Z` (общие шаги — в вызываемом
  `release-binaries.yml`), `dependabot.yml` обновляет модули Go и GitHub Actions.

### Изменилось

- `databases.owner` по умолчанию — владелец кластера (`postgres`): созданные базы
  принадлежат ему, а не роли, под которой работает сервис;
- подсказки `doctor` больше не ссылаются на отсутствующие в поставке файлы
  (`deploy/systemd`, `deploy/nftables/sqlbrc.nft`): говорится о самостоятельном
  создании юнита, ограничении доступа на межсетевом экране и о cron до появления таймера;
- описание команд в справке CLI: вместо «команды появятся в 0.2.0» перечислены
  фактические операции и коды возврата;
- `golang.org/x/crypto` обновлён до `v0.55.0` (был `v0.43.0`): в старых версиях есть уязвимости
  уровня HIGH в пакетах `x/crypto/ssh`, из-за которых файловая система сервиса не проходит «ворота»
  Trivy. Версия выбрана максимальной из совместимых с объявленной в `go.mod`: `v0.56.0` требует Go 1.26.

### Известные ограничения

- Веб-интерфейс и API, поставка в контейнере и режим `postgres.mode: tcp` — 0.3.0.
- RESTORE и CLONE не создают снимок кластера: одновременно идущие операции по одной базе
  ограничены `jobs.max_per_db`, но между сервисом и другими пользователями сервера
  синхронизации нет.
- Восстановление в отсутствующую базу создаёт её с локалью по умолчанию сервера
  (клонирование берёт локаль источника): если нужна конкретная локаль, создайте базу заранее.

## [0.1.0] - 2026-09-21

Первый выпуск: проверка готовности сервера, конфигурация и утилиты PostgreSQL.

### Add

- `SQL backup restore clone` (`sqlbrc`) — сервис для баз PostgreSQL 15 на одном сервере. В 0.1.0:
  - команда `doctor`: проверки конфига, утилит PostgreSQL, правила sudoers, прав и каталогов,
    свободного места, локалей, AppArmor, юнита systemd, веб-доступа, ролей и свежести бэкапов
    с уровнями `ok`/`warn`/`error`, подсказкой к каждой находке и кодом возврата 1 при ошибках;
  - форматы отчёта `table` и `json` (`--format`), журнал в `text`/`json` (`--log-format`);
  - конфигурация из YAML с переопределением переменными окружения `SQLBRC_*` (адрес, каталоги,
    пороги, TLS, уровень журнала) и проверкой значений при загрузке;
  - работа с утилитами PostgreSQL 15 через `sudo -n -u postgres`: пароли не хранятся, подключение
    идёт через локальный сокет, шаблон обслуживаемых баз (`databases.pattern`) задаёт список защищённых имён;
  - сборка и проверки: `Makefile`, `.golangci.yml`, юнит-тесты и fuzz-цели на разбор имён баз
    и вывода утилит, пример конфига `deploy/config.example.yaml`.
- CI: `ci.yml` собирает и проверяет оба инструмента (`cio` и `sqlbrc`: линт, `govulncheck`, тесты, сборка).
- Документация: `README.md` сервиса и этот `CHANGELOG.md`; корневой `README.md` описывает оба инструмента.

### Изменилось

- `databases.pattern` обязан быть заякорен (`^…$`): незаякоренный шаблон отвергается при проверке конфига,
  потому что применяется через `MatchString` и совпал бы с частью имени — шаблон вида `[0-9]+$` объявил бы
  «своей» чужую базу `prod-1`, а при восстановлении сервис базу очищает (`--clean --if-exists`);
- шаблон из `databases.pattern` передаётся в сборку аргументов `pg_dump`/`pg_restore`
  (`pg.DumpArgs.Pattern`, `pg.RestoreArgs.Pattern`, пустое значение — шаблон по умолчанию): сужение шаблона
  в конфиге действует и на запуск утилит, а не только на список обслуживаемых баз.

### Известные ограничения

- В 0.1.0 доступны команды `doctor` и `version`: операции, каталог бэкапов и журнал задач
  добавлены в 0.2.0 (веб-интерфейс, API и поставка в контейнере — 0.3.0).
- PITR и инкрементальные бэкапы не поддерживаются: план — логический дамп `pg_dump --format custom`.
- Сервис рассчитан на один сервер (PostgreSQL и каталог бэкапов рядом), подключение через локальный сокет.
