# SQL backup, restore and clone (`sqlbrc`)

## Суть

`sqlbrc` — сервис для PostgreSQL на одном сервере, который отвечает на три вопроса:

- **где бэкап** — `pg_dump --format custom --compress 6` в каталог сервиса, с политикой хранения и контролем
  свободного места;
- **как восстановить** — разворот базы из бэкапа: отсутствующая база создаётся, существующая
  очищается, активные подключения завершаются;
- **как получить копию стенда** — клонирование базы в стенд вида `<префикс>-<номер>`
  (`fse-1234`, `fssd-7`, `dops-fix-42`), которые создаются в пайплайне.

Управление — CLI и веб-интерфейс с одинаковыми операциями. Сервис рассчитан на сервер, где
PostgreSQL и каталог бэкапов лежат рядом, а доступ к интерфейсу есть только у ответственных людей.

## Зачем это нужно

Бэкап и разворот стенда обычно делают руками по ssh: аргументы `pg_dump` вспоминают заново, сессии
перед `pg_restore` не завершают, а старые дампы чистят тогда, когда кончилось место. `sqlbrc`
превращает это в одну операцию с проверками и журналом.

| Боль | Что делает `sqlbrc` |
| --- | --- |
| «перед релизом нужен бэкап, а команда каждый раз собирается заново» | одна операция (CLI или кнопка в веб-интерфейсе) вместо набора аргументов `pg_dump` |
| «`pg_restore` упал: объекты кем-то используются» | `databases.terminate_on_restore` — завершение подключений (`pg_terminate_backend`) перед разворотом |
| «восстановили не на ту базу» | сервис работает только с именами из `databases.pattern`; служебные базы и `databases.protected` не трогает никогда |
| «диск кончился на середине дампа» | `storage.min_free_space` — при малом остатке новые бэкапы не создаются; `keep_last` и `keep_days` — ротация старых |
| «нужна копия данных на стенд» | клонирование в стенд `<префикс>-<номер>`, в том числе из свежего бэкапа |
| «непонятно, почему сервис не работает на сервере» | `sqlbrc doctor`: sudo, версии утилит и сервера, права каталогов и место, локали, чтение архива, юнит systemd, безопасность интерфейса, свежесть бэкапов |
| «нужно встроить проверку в CI и мониторинг» | `doctor --format json` и код возврата 1 при ошибках |

## Возможности

Сервис развивается по версиям: 0.1.0 — фундамент (конфиг, доступ к PostgreSQL, диагностика),
0.2.0 — операции и веб-интерфейс.

| Возможность | Версия |
| --- | --- |
| конфиг YAML по схеме с проверкой значений; переопределение полей переменными `SQLBRC_*` | 0.1.0 |
| запуск утилит PostgreSQL через `sudo -n -u <владелец кластера>`: пароли не нужны (peer через локальный сокет) | 0.1.0 |
| сборка argv `pg_dump`, `pg_restore`, `psql` массивом (без шелла) и проверка имени БД перед операцией | 0.1.0 |
| разбор вывода утилит: версии клиента и сервера, роль, список баз, оглавление архива | 0.1.0 |
| `sqlbrc doctor`: проверки готовности сервера, форматы `table` и `json`, код возврата 1 при ошибках | 0.1.0 |
| бэкап, восстановление и клонирование: CLI и веб-интерфейс, каталог бэкапов, задачи с ограничением параллелизма | 0.2.0 |
| поставка в контейнере, режим `postgres.mode: tcp` с `PGPASSFILE` | 0.2.0 |

## Преимущества и отличия

`sqlbrc` не заменяет средства резервного копирования с журналом транзакций: он закрывает
повседневную задачу — «снять бэкап стенда и развернуть его» — на том же сервере, где работает
PostgreSQL.

| Инструмент | Что даёт | Чего не хватает для регулярной работы |
| --- | --- | --- |
| `pg_dump` и `pg_restore` вручную | полный контроль над аргументами | нет журнала и истории, легко перепутать базу; место и ротация — забота администратора |
| `pgBackRest`, `WAL-G` | инкрементальные и непрерывные бэкапы, PITR | сложнее в установке; рутинные «бэкап стенда и разворот» остаются командами CLI |
| pgAdmin и другие web-UI | визуальный доступ к базе | бэкап и восстановление — ручные операции, политик хранения и проверок нет |
| `sqlbrc` | операции бэкапа, восстановления и клонирования с проверками, политикой хранения и журналом | нет PITR и инкрементальных бэкапов, работа только с одним сервером |

Что это даёт на практике:

- одна проверяемая операция вместо набора аргументов: имя базы проходит проверку по шаблону, а не
  подставляется в командную строку;
- политика хранения и контроль свободного места выполняются сервисом, а не «когда-нибудь руками»;
- `sqlbrc doctor` показывает, чего не хватает серверу (локали, права каталогов, AppArmor, юнит
  systemd), до первой операции, а не после упавшего `pg_restore`;
- отчёт `doctor` в JSON и код возврата 1 позволяют поставить проверку в CI и в мониторинг.

## Требования

| Компонент | Версия | Обязателен |
| --- | --- | --- |
| PostgreSQL (сервер) | 15 | да: операции выполняются утилитами PostgreSQL |
| Утилиты PostgreSQL (`pg_dump`, `pg_restore`, `psql`, `pg_isready`) | та же мажорная версия, что и сервер | да: расхождение версий клиента и сервера `doctor` проверяет отдельно |
| Linux + systemd | Debian 12, Ubuntu 22.04+ и подобные | да: `sudo`, права каталогов, юнит сервиса |
| `sudo` | правило `NOPASSWD` на фиксированный список утилит | да: утилиты запускаются от владельца кластера без пароля |
| Go | 1.25.14+ | только для сборки из исходников: минимальный патч зафиксирован в `go.mod` |

## Установка и первый запуск

1. Собрать бинарь (см. «Сборка и запуск»).
2. Создать каталоги и конфиг:

   ```bash
   install -d -m 0750 /etc/sqlbrc
   install -m 0640 deploy/config.example.yaml /etc/sqlbrc/config.yaml
   install -d -m 0750 -o sqlbrc -g sqlbrc /var/backups/sqlbrc /var/lib/sqlbrc
   ```

   `storage.dir` — отдельный каталог сервиса, а не `/var/backups` целиком: политика хранения
   удаляет старые дампы, поэтому рядом не должно быть чужих файлов. `storage.state_dir` хранит
   журнал задач и аудит, поэтому он закрыт (0700).
3. Разрешить пользователю сервиса запуск утилит PostgreSQL — `/etc/sudoers.d/sqlbrc` (режим 0440):

   ```
   sqlbrc ALL=(postgres) NOPASSWD: /usr/bin/pg_dump, /usr/bin/pg_restore, /usr/bin/psql, /usr/bin/pg_isready
   ```

   Список утилит фиксирован; правило вида `postgres ALL` избыточно и расширяет права сервиса.
4. Править `/etc/sqlbrc/config.yaml`: привести `databases.pattern` к именам стендов своей команды и
   задать `auth.users`. Без команды `sqlbrc hash-password` (0.2.0) bcrypt-хэш пароля создаётся так:
   `htpasswd -bnBC 10 "" 'пароль' | tr -d ':\n'`.
5. Проверить сервер до первой операции: `sqlbrc doctor`; для CI и мониторинга — `sqlbrc doctor --format json`.

## Сборка и запуск

```powershell
# Windows
go build -o bin/sqlbrc.exe ./cmd/sqlbrc
./bin/sqlbrc.exe doctor --config deploy/config.example.yaml
```

```bash
# Linux, macOS или среда с make
make build
./bin/sqlbrc doctor --config deploy/config.example.yaml
```

Версия подставляется в бинарь при сборке: `make build` берёт её из `git describe`, CI — из коммита,
релиз — из тега. `sqlbrc --version` печатает версию, коммит и дату сборки. История изменений —
в [CHANGELOG.md](CHANGELOG.md).

## Конфигурация

Настройки живут в одном файле YAML, значения по умолчанию рассчитаны на Debian с PostgreSQL 15.
Любое поле можно переопределить переменной окружения `SQLBRC_<РАЗДЕЛ>_<ПОЛЕ>`; полный список переменных
печатает `sqlbrc doctor --help`. Хэши паролей и пути к файлам секретов вырезаются перед записью в журнал.

| Раздел | Зачем | Ключевые поля |
| --- | --- | --- |
| `server` | веб-интерфейс | `listen`, `tls.cert_file` / `tls.key_file`, `allow_insecure`, `read_only`, `max_body_bytes`, `public_url` |
| `auth` | доступ к интерфейсу и API | `users[].login` и `password_bcrypt`, `token_file`, `session_ttl`, `login_backoff`, `max_login_attempts` |
| `postgres` | как сервис работает с PostgreSQL | `mode`, `sudo_path`, `sudo_user`, `bin_dir`, `database`, `role` и `password_file`, `jobs`, `timeout` |
| `storage` | где лежат бэкапы и служебные данные | `dir`, `state_dir`, `keep_last`, `keep_days`, `min_free_space` |
| `databases` | какие базы обслуживаются | `pattern`, `protected`, `owner`, `auto_backup_before_restore`, `terminate_on_restore` |
| `jobs` | очередь операций | `max_parallel`, `max_per_db`, `retain` |
| `logging` | журнал сервиса | `level`, `format` |

Что проверяется до запуска (те же замечания показывает `sqlbrc doctor`):

- `schema_version` совпадает с поддерживаемым: неизвестная версия схемы отвергается, а не толкуется «как получится»;
- `server.listen` — корректный `host:port`; интерфейс на не-loopback адресе без TLS не запустится без явного `allow_insecure`; `max_body_bytes` — в диапазоне 4 КиБ..64 МиБ;
- `auth`: логины (строчные латинские буквы, цифры, `_`, `-`, `.`, 3..32 символа) уникальны, `password_bcrypt` — bcrypt-хэш длиной 60 символов, `session_ttl` не больше 168 ч, `max_login_attempts` — 1..100;
- `postgres`: в 0.1.0 поддержан только `mode: sudo`; при нём `role` из конфига не применяется — владелец объектов берётся из дампа (`databases.owner`);
- `storage`: пути абсолютные, `state_dir` не совпадает с `dir`, `keep_last` — 1..1000, `keep_days` — 1..3650, `min_free_space` больше нуля и не больше 1 ТиБ;
- `databases`: `pattern` компилируется и заякорен (`^…$`: незаякоренный совпал бы с частью имени), `protected` не пуст, `owner` — допустимый идентификатор;
- `jobs`: `max_parallel` и `max_per_db` — 1..16, `max_per_db` не больше `max_parallel`, `retain` — 10..100000;
- `logging`: `level` из `debug`, `info`, `warn`, `error`; `format` из `text`, `json`.

Фрагмент конфига (полный образец — `deploy/config.example.yaml`):

```yaml
schema_version: 1

server:
  listen: "0.0.0.0:8088"
  allow_insecure: true      # слушаем LAN по HTTP: порт закрыт межсетевым экраном

postgres:
  mode: "sudo"              # sudo -n -u postgres через локальный сокет, пароли не хранятся
  sudo_user: "postgres"

storage:
  dir: "/var/backups/sqlbrc"
  keep_last: 7
  keep_days: 14
  min_free_space: "5GB"

databases:
  pattern: "^[a-z][a-z0-9]*(?:-[a-z0-9]+)*-[0-9]+$"
```

## Как это работает

1. `internal/config` — читает YAML, подставляет значения по умолчанию, переопределяет поля переменными
   `SQLBRC_*` и проверяет результат: за один запуск печатается полный список замечаний, а не первое.
2. `internal/pg` — единственное место, где сервис говорит с PostgreSQL:
   - `argv.go` собирает аргументы `pg_dump`, `pg_restore` и `psql` массивом строк и проверяет
     значения (имя базы — по шаблону из `databases.pattern`, формат, уровень сжатия, разделитель);
   - `runner.go` запускает процесс без промежуточного шелла и печатает команду в читаемом виде;
   - `parse.go` разбирает версии утилит и сервера, вывод `psql` и оглавление архива;
   - `client.go` — запросы к каталогу (роль, список баз, доступность сервера),
     `dbname.go` — проверка имён баз и идентификаторов бэкапов.
3. `internal/doctor` — проверки готовности сервера поверх интерфейсов PostgreSQL, файловой системы и
   запуска процессов: отчёт в `table` или `json`, код возврата 1 при ошибках.
4. `internal/bytesize` — размеры в человекочитаемом виде (`5GB`) для конфига и отчёта.

Все внешние эффекты закрыты интерфейсами, поэтому тесты не поднимают PostgreSQL, не выполняют `sudo` и не
зависят от платформы разработки.

## Безопасность

- Аргументы собираются массивом, промежуточного шелла нет: имя базы из формы или из скрипта не станет частью
  команды. `pg.ValidateDBName` пропускает только строчные латинские буквы, цифры, `_`, `-`, `.`, требует
  совпадения с `databases.pattern` и отдельно отвергает обход каталогов (`../../etc/passwd`).
- Шаблон обслуживаемых баз обязан быть заякорен (`^…$`): незаякоренный отвергается при проверке конфига
  и не проходит в argv. Иначе совпадение нашлось бы в середине имени, и «своей» стала бы чужая база —
  а при восстановлении сервис очищает базу (`--clean --if-exists`).
- Пароли не хранятся: 0.1.0 работает через peer-аутентификацию и `sudo -n -u <владелец кластера>`,
  контейнерный режим (0.2.0) — через `PGPASSFILE` с правами 0600.
- Правило sudoers перечисляет утилиты поимённо: `pg_dump`, `pg_restore`, `psql`, `pg_isready`.
  Правило вида `postgres ALL` сервису не нужно и расширяет его права.
- `storage.dir` — отдельный каталог сервиса: политика хранения удаляет старые дампы, поэтому рядом не должно
  быть чужих файлов. `storage.state_dir` закрыт (0700) и не совпадает с каталогом бэкапов.
- `doctor` проверяет чтение архива пользователем кластера: отказы AppArmor не видны по правам каталога,
  а всплывают только при восстановлении.
- Веб-интерфейс (0.2.0): встроенные пользователи с bcrypt-хэшами, токены в отдельном файле, TTL сессии,
  задержка между попытками входа и их предел; `read_only` запрещает изменяющие операции.

`name`, `level`, `message`, `hint`.

(`deploy/nftables/sqlbrc.nft`), на которые ссылаются подсказки `doctor`, появятся вместе с операциями
бэкапа в 0.2.0.

## Ограничения

- **Логический бэкап, а не PITR.** `pg_dump --format custom --compress 6`: восстановление возможно только на
  момент снятия дампа. Непрерывного архивирования WAL и инкрементальных бэкапов нет.
- **Один сервер.** Сервис рассчитан на случай, когда PostgreSQL и каталог бэкапов лежат рядом: подключение
  идёт через локальный сокет. Режим `tcp` для удалённого сервера и поставка в контейнере — 0.2.0.
- **Восстановление — это разворот базы целиком.** Отдельную таблицу или строку из дампа вернуть нельзя:
  база очищается (`--clean --if-exists`) и разворачивается заново.
- **Сервис трогает только «свои» базы.** Имя должно совпадать с `databases.pattern` и не попадать в
  `databases.protected`, а сам шаблон обязан быть заякорен (`^…$`). Шаблон по умолчанию описывает
  строчные имена вида `<префикс>-<номер>`: `fse-1234`, `dops-fix-42` (префикс может состоять из
  нескольких сегментов через дефис), при этом номер в конце обязателен. Имя без номера в конце,
  с подчёркиванием или в верхнем регистре под шаблон не подходит — для таких стендов нужен свой
  `databases.pattern`.
- **Linux.** Проверки каталогов, прав, локалей, AppArmor и юнита systemd рассчитаны на Debian и подобные
  системы: на другой платформе `doctor` честно сообщит, что проверить не удалось.
- **Тестовый сценарий по умолчанию — логин и пароль.** Интеграции с Keycloak/OIDC нет; TLS либо
  настраивается в сервисе, либо подразумевает reverse-proxy (в планах — `--listen 127.0.0.1:8088`,
  cookie/CSRF).
- **Политика хранения удаляет файлы** в `storage.dir`: каталог должен принадлежать сервису целиком.

## Разработка

| Команда | Что делает |
| --- | --- |
| `make` (`make all`) | обычная локальная проверка: `fmt`, `vet`, `test`, `build` |
| `make build` | собирает `bin/sqlbrc` с версией, коммитом и датой сборки (`make build VERSION=0.1.0` переопределяет версию) |
| `make version` | собирает бинарь и печатает `sqlbrc --version` |
| `make test` | `go test ./... -count=1` |
| `make vet` | `go vet ./...` |
| `make fmt` | `gofmt -l -w cmd internal` (а `make fmt-check` только показывает файлы) |
| `make lint` | `golangci-lint run ./...` с правилами из `.golangci.yml` |
| `make tidy` | `go mod tidy` |
| `make clean` | `go clean` и удаление `bin/` |

Тесты живут рядом с кодом (`*_test.go` в том же пакете), данные — в `testdata/`. Внешние процессы
(PostgreSQL, `sudo`) в тестах не запускаются: зависимости подменяются через интерфейсы, поэтому проверки
идут без сервера и на любой платформе разработки. Отдельные цели `cover` и `fuzz` в `Makefile` не
описываются, потому что они не нужны в CI: покрытие считает `go test -coverprofile`, fuzz-цели запускаются
как `go test -fuzz=Fuzz… ./internal/config`.

## Планы

- **0.2.0** — команды бэкапа, восстановления и клонирования в CLI, каталог бэкапов с политикой хранения,
  фоновые задачи и журнал, веб-интерфейс и API, поставка в контейнере (`postgres.mode: tcp`).
