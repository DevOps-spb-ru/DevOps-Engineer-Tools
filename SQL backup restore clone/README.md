# SQL backup, restore and clone (`sqlbrc`)

## Суть

`sqlbrc` — сервис для PostgreSQL на одном сервере, который отвечает на три вопроса:

- **где бэкап** — `pg_dump --format custom --compress 6` в каталог сервиса, с политикой хранения и контролем
  свободного места;
- **как восстановить** — разворот базы из бэкапа: отсутствующая база создаётся, существующая
  очищается, активные подключения завершаются;
- **как получить копию стенда** — клонирование базы в стенд вида `<префикс>-<номер>`
  (`fse-1234`, `fssd-7`, `dops-fix-42`), которые создаются в пайплайне.

Управление — CLI и веб-интерфейс с API: операции одинаковы для человека, для пайплайна
(стенды создаются автоматически) и для кнопки в браузере — `sqlbrc serve` поднимает интерфейс
и API поверх тех же операций. Сервис рассчитан на сервер, где PostgreSQL и каталог бэкапов
лежат рядом, а доступ к конфигу есть только у ответственных людей.

## Зачем это нужно

Бэкап и разворот стенда обычно делают руками по ssh: аргументы `pg_dump` вспоминают заново, сессии
перед `pg_restore` не завершают, а старые дампы чистят тогда, когда кончилось место. `sqlbrc`
превращает это в одну операцию с проверками и журналом.

| Боль | Что делает `sqlbrc` |
| --- | --- |
| «перед релизом нужен бэкап, а команда каждый раз собирается заново» | одна операция (CLI или кнопка в веб-интерфейсе) вместо набора аргументов `pg_dump` |
| «`pg_restore` упал: объекты кем-то используются» | `databases.terminate_on_restore` — завершение подключений (`pg_terminate_backend`) перед разворотом |
| «восстановили не на ту базу» | сервис работает только с именами из `databases.pattern`; служебные базы и `databases.protected` не трогает никогда |
| «диск кончился на середине дампа» | `storage.min_free_space` — при малом остатке новые бэкапы не создаются; `keep_last` и `keep_days` — ротация старых |
| «нужна копия данных на стенд» | клонирование в стенд `<префикс>-<номер>`, в том числе из свежего бэкапа |
| «непонятно, почему сервис не работает на сервере» | `sqlbrc doctor`: sudo, версии утилит и сервера, права каталогов и место, локали, чтение архива, юнит systemd, безопасность интерфейса, свежесть бэкапов |
| «нужно встроить проверку в CI и мониторинг» | `doctor --format json` и код возврата 1 при ошибках |

## Возможности

Сервис развивается по версиям: 0.1.0 — фундамент (конфиг, доступ к PostgreSQL,
диагностика), 0.2.0 — операции, каталог бэкапов и журнал задач, 0.3.0 — веб-интерфейс,
API и поставка в контейнере.

| Возможность | Версия |
| --- | --- |
| конфиг YAML по схеме с проверкой значений; переопределение полей переменными `SQLBRC_*` | 0.1.0 |
| запуск утилит PostgreSQL через `sudo -n -u <владелец кластера>`: пароли не нужны (peer через локальный сокет) | 0.1.0 |
| сборка argv `pg_dump`, `pg_restore`, `psql` массивом (без шелла) и проверка имени БД перед операцией | 0.1.0 |
| разбор вывода утилит: версии клиента и сервера, роль, список баз, оглавление архива | 0.1.0 |
| `sqlbrc doctor`: проверки готовности сервера, форматы `table` и `json`, код возврата 1 при ошибках | 0.1.0 |
| `sqlbrc backup`, `restore`, `clone`: бэкап базы, разворот из бэкапа и стенд из бэкапа другой базы | 0.2.0 |
| каталог бэкапов: файл метаданных, контрольная сумма, политика хранения, контроль свободного места | 0.2.0 |
| очередь задач с `jobs.max_parallel` и `jobs.max_per_db`, журнал задач `sqlbrc jobs` | 0.2.0 |
| служебный бэкап с меткой `pre-restore` перед восстановлением и завершение активных подключений | 0.2.0 |
| `sqlbrc hash-password`: bcrypt-хэш пароля для `auth.users` | 0.2.0 |
| код возврата 2 для операции, отвергнутой до начала (чужая база, `read_only`, мало места) | 0.2.0 |
| веб-интерфейс и API для тех же операций | 0.3.0 |
| поставка в контейнере, режим `postgres.mode: tcp` с `PGPASSFILE` | 0.3.0 |

## Преимущества и отличия

`sqlbrc` не заменяет средства резервного копирования с журналом транзакций: он закрывает
повседневную задачу — «снять бэкап стенда и развернуть его» — на том же сервере, где работает
PostgreSQL.

| Инструмент | Что даёт | Чего не хватает для регулярной работы |
| --- | --- | --- |
| `pg_dump` и `pg_restore` вручную | полный контроль над аргументами | нет журнала и истории, легко перепутать базу; место и ротация — забота администратора |
| `pgBackRest`, `WAL-G` | инкрементальные и непрерывные бэкапы, PITR | сложнее в установке; рутинные «бэкап стенда и разворот» остаются командами CLI |
| pgAdmin и другие web-UI | визуальный доступ к базе | бэкап и восстановление — ручные операции, политик хранения и проверок нет |
| `sqlbrc` | операции бэкапа, восстановления и клонирования с проверками, политикой хранения и журналом | нет PITR и инкрементальных бэкапов, работа только с одним сервером |

Что это даёт на практике:

- одна проверяемая операция вместо набора аргументов: имя базы проходит проверку по шаблону, а не
  подставляется в командную строку;
- политика хранения и контроль свободного места выполняются сервисом, а не «когда-нибудь руками»;
- `sqlbrc doctor` показывает, чего не хватает серверу (локали, права каталогов, AppArmor, юнит
  systemd), до первой операции, а не после упавшего `pg_restore`;
- отчёт `doctor` в JSON и код возврата 1 позволяют поставить проверку в CI и в мониторинг.

## Требования

| Компонент | Версия | Обязателен |
| --- | --- | --- |
| PostgreSQL (сервер) | 15 | да: операции выполняются утилитами PostgreSQL |
| Утилиты PostgreSQL (`pg_dump`, `pg_restore`, `psql`, `pg_isready`) | та же мажорная версия, что и сервер | да: расхождение версий клиента и сервера `doctor` проверяет отдельно |
| Linux + systemd | Debian 12, Ubuntu 22.04+ и подобные | да: `sudo`, права каталогов, юнит сервиса |
| `sudo` | правило `NOPASSWD` на фиксированный список утилит | да: утилиты запускаются от владельца кластера без пароля |
| Go | 1.26.8+ | только для сборки из исходников: минимальный патч зафиксирован в `go.mod` |

## Установка и первый запуск

1. Собрать бинарь (см. «Сборка и запуск»).
2. Создать каталоги и конфиг:

   ```bash
   install -d -m 0750 /etc/sqlbrc
   install -m 0640 deploy/config.example.yaml /etc/sqlbrc/config.yaml
   install -d -m 0750 -o sqlbrc -g sqlbrc /var/backups/sqlbrc /var/lib/sqlbrc
   ```

   `storage.dir` — отдельный каталог сервиса, а не `/var/backups` целиком: политика хранения
   удаляет старые дампы, поэтому рядом не должно быть чужих файлов. `storage.state_dir` хранит
   журнал задач и аудит, поэтому он закрыт (0700).
3. Разрешить пользователю сервиса запуск утилит PostgreSQL — `/etc/sudoers.d/sqlbrc` (режим 0440):

   ```
   sqlbrc ALL=(postgres) NOPASSWD: /usr/bin/pg_dump, /usr/bin/pg_restore, /usr/bin/psql, /usr/bin/pg_isready
   ```

   Список утилит фиксирован; правило вида `postgres ALL` избыточно и расширяет права сервиса.
4. Править `/etc/sqlbrc/config.yaml`: привести `databases.pattern` к именам стендов своей команды и
   задать `auth.users`. Хэш пароля создаётся командой:
   `printf '%s' 'пароль' | sqlbrc hash-password --login admin` — она печатает готовый фрагмент
   `auth.users` (пароль из аргументов не принимается: аргументы видны в списке процессов).
5. Проверить сервер до первой операции: `sqlbrc doctor`; для CI и мониторинга — `sqlbrc doctor --format json`.
6. Первый бэкап и список: `sqlbrc backup --db fse-1234`, затем `sqlbrc backups list`.

## Сборка и запуск

```powershell
# Windows
go build -o bin/sqlbrc.exe ./cmd/sqlbrc
./bin/sqlbrc.exe doctor --config deploy/config.example.yaml
```

```bash
# Linux, macOS или среда с make
make build
./bin/sqlbrc doctor --config deploy/config.example.yaml
```

Версия подставляется в бинарь при сборке: `make build` берёт её из `git describe`, CI — из коммита,
релиз — из тега. `sqlbrc --version` печатает версию, коммит и дату сборки. История изменений —
в [CHANGELOG.md](CHANGELOG.md).

## Команды и флаги

| Команда | Что делает |
| --- | --- |
| `sqlbrc backup --db <имя> [--tag <метка>] [--note <текст>]` | снимает дамп базы в каталог сервиса, затем применяет политику хранения |
| `sqlbrc backup --all [--tag <метка>] [--note <текст>]` | снимает бэкапы всех обслуживаемых баз кластера: одна недоступная база не отменяет остальные |
| `sqlbrc restore --db <имя> [--backup <идентификатор>] [--no-clean]` | разворачивает базу из бэкапа (по умолчанию — последнего): снимает служебный бэкап `pre-restore`, завершает активные подключения, создаёт отсутствующую базу и очищает существующую |
| `sqlbrc clone --from <источник> --to <стенд> [--backup <идентификатор>]` | создаёт стенд из бэкапа другой базы: локаль берётся у источника, существующий приёмник не перезаписывается |
| `sqlbrc backups list [--db <имя>]` | показывает бэкапы: идентификатор, время, размер, метка, состояние |
| `sqlbrc backups prune [--db <имя>] [--dry-run]` | удаляет старые бэкапы и незавершённые записи по политике хранения; `--dry-run` показывает план |
| `sqlbrc jobs [--limit N] [--json]` | показывает журнал задач: вид операции, база, состояние, время, итог |
| `sqlbrc hash-password --login <имя>` | печатает фрагмент `auth.users` с bcrypt-хэшем пароля (пароль читается из stdin) |
| `sqlbrc serve [--listen <адрес>]` | поднимает веб-интерфейс и API; вход по `auth.users`, API — по токену из `auth.token_file` |
| `sqlbrc doctor [--format table\|json]` | проверяет готовность сервера; код возврата 1, если есть ошибки |
| `sqlbrc version` | печатает версию, коммит и дату сборки (то же, что `--version`) |

Коды возврата: `0` — успех, `1` — ошибка (конфиг, сбой утилиты, недоступный сервер),
`2` — операция отвергнута до начала: чужая или защищённая база, `server.read_only`,
остаток места меньше `storage.min_free_space`. Код `2` означает, что сервис не тронул
ни базу, ни файлы: скрипт может отличить отказ от сбоя.

| Глобальный флаг | По умолчанию | Назначение |
| --- | --- | --- |
| `--config` | `$SQLBRC_CONFIG`, затем `/etc/sqlbrc/config.yaml` | путь к конфигу; приоритет: флаг → переменная окружения → путь по умолчанию |
| `--log-level` | из `logging.level` | `debug`, `info`, `warn` или `error` |
| `--log-format` | из `logging.format` | `text` или `json` |
| `--version` | — | версия, коммит и дата сборки |

## Веб-интерфейс и API

`sqlbrc serve` поднимает тот же сервис, но с интерфейсом для браузера и API для скриптов:
операции, проверки и журнал те же, что в CLI, поэтому кнопка в браузере не обходит ни
`databases.pattern`, ни `server.read_only`.

| Что | Как |
| --- | --- |
| страницы | «Базы и бэкапы» (`/`) — список баз, бэкапы, формы бэкапа, клонирования и уборки; «Журнал задач» (`/jobs`) |
| вход | `auth.users` (bcrypt-хэш из `sqlbrc hash-password`); сессия живёт `auth.session_ttl`, cookie — `HttpOnly` + `SameSite=Strict` |
| API | `/api/v1/backups`, `/api/v1/jobs` — чтение; `/api/v1/backup`, `/api/v1/restore`, `/api/v1/clone`, `/api/v1/prune` — операции |
| доступ к API | токен из `auth.token_file` (файл вида `<логин>:<токен>`, по строке на токен) в заголовке `Authorization: Bearer …` |
| проверка живости | `GET /healthz` отвечает `ok` без аутентификации (для systemd и мониторинга) |

```bash
sqlbrc serve --config /etc/sqlbrc/config.yaml   # адрес из server.listen (0.0.0.0:8088)
sqlbrc serve --listen 127.0.0.1:8088            # только локально: TLS не нужен

TOKEN=$(grep '^ci:' /etc/sqlbrc/tokens | cut -d: -f2)
curl -s -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:8088/api/v1/backups?db=fse-1234'
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"database":"fse-1234","tag":"before-release"}' http://127.0.0.1:8088/api/v1/backup
```

Коды ответов API: `200`/`201` — успех, `400` — запрос не разобран (`invalid_request`),
`401` — нет или не тот токен (`unauthorized`), `403` — режим `server.read_only` (`forbidden`),
`409` — операция отвергнута по правилам: чужая база, существующий приёмник, мало места
(`rejected`), `500` — сбой (`internal`). Тело ошибки — `{"error":{"type":"…","message":"…"}}`.

Что защищено:

- изменяющие формы проверяют CSRF-токен сессии: сторонний сайт не отправит операцию от имени
  вошедшего человека;
- cookie-сессия не даёт доступа к API (там только токен): иначе защита от CSRF теряла бы смысл;
- неудачные попытки входа ограничены: пауза `auth.login_backoff` растёт, после
  `auth.max_login_attempts` вход по логину временно блокируется;
- размер запроса ограничен `server.max_body_bytes`, ответы получают заголовки
  `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` и `Content-Security-Policy`;
- адрес клиента в журнале берётся из `X-Forwarded-For` только от `server.trusted_proxies`;
- если сервис слушает не loopback без TLS, при запуске печатается предупреждение, а `doctor`
  показывает это отдельным замечанием.

## Поставка

Сервис разворачивается двумя способами: на сервере рядом с PostgreSQL (режим `sudo`, локальный
сокет) или в контейнере, подключающемся к серверу по сети (режим `tcp`). Файлы поставки лежат
в `deploy/`.

### systemd (сервер рядом с PostgreSQL)

| Файл | Что делает |
| --- | --- |
| `deploy/systemd/sqlbrc.service` | служба `sqlbrc serve`: конфиг `/etc/sqlbrc/config.yaml`, ограничения `ProtectSystem=strict`, `ReadWritePaths` только на каталоги сервиса |
| `deploy/systemd/sqlbrc-backup.service` + `.timer` | ежедневный бэкап всех обслуживаемых баз (`backup --all`): 02:30 со случайным разбросом, пропущенный запуск выполняется после включения машины |

```bash
install -m 0644 deploy/systemd/sqlbrc.service deploy/systemd/sqlbrc-backup.service \
  deploy/systemd/sqlbrc-backup.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now sqlbrc.service sqlbrc-backup.timer
```

Расписание без systemd — `deploy/cron.d/sqlbrc` (одна строка cron с `backup --all`).
Доступ к интерфейсу ограничивается межсетевым экраном: `deploy/nftables/sqlbrc.nft`
(проверка без применения — `nft -c -f deploy/nftables/sqlbrc.nft`).

### Контейнер

В контейнере сервис работает в режиме `postgres.mode: tcp`: локального сокета и
peer-аутентификации там нет, поэтому подключение идёт по сети от имени роли, а пароль
передаётся файлом (PGPASSFILE). Файл создаёт точка входа образа
(`deploy/docker-entrypoint.sh`) из переменной `SQLBRC_PGPASS` — сразу с правами 0600:
смонтированный с хоста файл прав не сохраняет, а PostgreSQL не читает pgpass, доступный
группе или остальным.

```bash
cp deploy/.env.example deploy/.env                          # пароль роли (POSTGRES_PASSWORD)
cp deploy/config.container.example.yaml deploy/config.yaml  # конфиг для контейнера
printf '%s' 'пароль' | bin/sqlbrc hash-password --login admin   # фрагмент auth.users
docker compose -f deploy/compose.example.yaml up -d --build
```

Стенд из `deploy/compose.example.yaml` поднимает PostgreSQL 15 и сервис рядом, публикует
интерфейс только на `127.0.0.1:8088` и хранит бэкапы и журнал задач в томах. Рабочие
`deploy/.env` и `deploy/config.yaml` в Git не попадают: в них пароль и настройки стенда.
В образе подставлены те же версия, коммит и дата сборки, что и в бинаре из релиза
(`sqlbrc --version` внутри контейнера), поэтому образ можно сверить с релизом.

## Конфигурация

Настройки живут в одном файле YAML, значения по умолчанию рассчитаны на Debian с PostgreSQL 15.
Любое поле можно переопределить переменной окружения `SQLBRC_<РАЗДЕЛ>_<ПОЛЕ>`; полный список переменных
печатает `sqlbrc doctor --help`. Хэши паролей и пути к файлам секретов вырезаются перед записью в журнал.

| Раздел | Зачем | Ключевые поля |
| --- | --- | --- |
| `server` | веб-интерфейс | `listen`, `tls.cert_file` / `tls.key_file`, `allow_insecure`, `read_only`, `max_body_bytes`, `public_url`, `trusted_proxies` |
| `auth` | доступ к интерфейсу и API | `users[].login` и `password_bcrypt`, `token_file` (формат `<логин>:<токен>`, образец — `deploy/tokens.example`), `session_ttl`, `login_backoff`, `max_login_attempts` |
| `postgres` | как сервис работает с PostgreSQL | `mode` (`sudo` — локальный сокет и peer, `tcp` — по сети с паролем из файла), `sudo_path`, `sudo_user`, `bin_dir`, `host`, `port`, `role`, `database`, `password_file`, `jobs`, `timeout` |
| `storage` | где лежат бэкапы и служебные данные | `dir`, `state_dir`, `keep_last`, `keep_days`, `min_free_space` |
| `databases` | какие базы обслуживаются | `pattern`, `protected`, `owner`, `auto_backup_before_restore`, `terminate_on_restore` |
| `jobs` | очередь операций | `max_parallel`, `max_per_db`, `retain` |
| `logging` | журнал сервиса | `level`, `format` |

Что проверяется до запуска (те же замечания показывает `sqlbrc doctor`):

- `schema_version` совпадает с поддерживаемым: неизвестная версия схемы отвергается, а не толкуется «как получится»;
- `server.listen` — корректный `host:port`; интерфейс на не-loopback адресе без TLS не запустится без явного `allow_insecure`; `max_body_bytes` — в диапазоне 4 КиБ..64 МиБ;
- `auth`: логины (строчные латинские буквы, цифры, `_`, `-`, `.`, 3..32 символа) уникальны, `password_bcrypt` — bcrypt-хэш длиной 60 символов, `session_ttl` не больше 168 ч, `max_login_attempts` — 1..100;
- `postgres`: `mode` — `sudo` (локальный сокет) или `tcp` (подключение по сети); в режиме `tcp` обязательны `host`, `port`, `role` и `password_file` (пароль передаётся файлом, а не аргументами команды), а в `sudo` роль из конфига не применяется — владелец объектов берётся из дампа (`databases.owner`);
- `storage`: пути абсолютные, `state_dir` не совпадает с `dir`, `keep_last` — 1..1000, `keep_days` — 1..3650, `min_free_space` больше нуля и не больше 1 ТиБ;
- `databases`: `pattern` компилируется и заякорен (`^…$`: незаякоренный совпал бы с частью имени), `protected` не пуст, `owner` — допустимый идентификатор;
- `jobs`: `max_parallel` и `max_per_db` — 1..16, `max_per_db` не больше `max_parallel`, `retain` — 10..100000;
- `logging`: `level` из `debug`, `info`, `warn`, `error`; `format` из `text`, `json`.

Фрагмент конфига (полный образец — `deploy/config.example.yaml`):

```yaml
schema_version: 1

server:
  listen: "0.0.0.0:8088"
  allow_insecure: true      # слушаем LAN по HTTP: порт закрыт межсетевым экраном

postgres:
  mode: "sudo"              # sudo -n -u postgres через локальный сокет, пароли не хранятся
  sudo_user: "postgres"

storage:
  dir: "/var/backups/sqlbrc"
  keep_last: 7
  keep_days: 14
  min_free_space: "5GB"

databases:
  pattern: "^[a-z][a-z0-9]*(?:-[a-z0-9]+)*-[0-9]+$"
```

## Как это работает

1. `internal/config` — читает YAML, подставляет значения по умолчанию, переопределяет поля переменными
   `SQLBRC_*` и проверяет результат: за один запуск печатается полный список замечаний, а не первое.
2. `internal/pg` — единственное место, где сервис говорит с PostgreSQL:
   - `argv.go` собирает аргументы `pg_dump`, `pg_restore` и `psql` массивом строк и проверяет
     значения (имя базы — по шаблону из `databases.pattern`, формат, уровень сжатия, разделитель);
   - `runner.go` запускает процесс без промежуточного шелла и печатает команду в читаемом виде;
   - `parse.go` разбирает версии утилит и сервера, вывод `psql` и оглавление архива;
   - `client.go` — запросы к каталогу (роль, список баз, доступность сервера),
     `dbname.go` — проверка имён баз и идентификаторов бэкапов;
   - `sql.go` и `databases.go` — служебные запросы и операции с базами: создание, владелец,
     локаль, размер, завершение активных подключений (`QuoteIdentifier`/`QuoteLiteral`
     собирают запрос из проверенных значений);
   - `dump.go`, `restore.go` и `wait.go` — дамп, восстановление и ожидание готовности сервера.
3. `internal/store` — каталог бэкапов: раскладка `<база>/<метка времени>[-<метка>].dump`
   с файлом метаданных (sha256, размер, параметры дампа), запись через `.part` с переименованием,
   поиск бэкапа, контроль свободного места и политика хранения (чистая функция `store.Plan`).
4. `internal/jobs` — очередь задач (пределы `jobs.max_parallel` и `jobs.max_per_db`) и журнал
   задач в формате JSONL: каждая задача записывается при запуске и по завершении.
5. `internal/backup` — операции сервиса: порядок проверок до первой команды (своя база,
   `server.read_only`, свободное место, контрольная сумма архива), служебный бэкап `pre-restore`,
   завершение подключений, разворот бэкапа и политика хранения после дампа.
6. `internal/doctor` — проверки готовности сервера поверх интерфейсов PostgreSQL, файловой системы и
   запуска процессов: отчёт в `table` или `json`, код возврата 1 при ошибках.
7. `internal/bytesize` и `internal/passwd` — размеры в человекочитаемом виде (`5GB`)
   и bcrypt-хэши паролей.
8. `internal/auth` — вход: bcrypt-хэши из `auth.users`, сессии в памяти с временем жизни
   `auth.session_ttl`, ограничение неудачных попыток входа и токены API из `auth.token_file`.
9. `internal/web` — веб-интерфейс и API: страницы, JSON-API, CSRF-токен сессии, cookie
   `HttpOnly`/`SameSite=Strict` и защитные заголовки. Интерфейс работает через операции сервиса
   (`backup.Service`), поэтому проверки и журнал у кнопки в браузере те же, что в CLI.

Все внешние эффекты закрыты интерфейсами, поэтому тесты не поднимают PostgreSQL, не выполняют `sudo`,
не трогают реальные каталоги сервера и не зависят от платформы разработки.

## Безопасность

- Аргументы собираются массивом, промежуточного шелла нет: имя базы из формы или из скрипта не станет частью
  команды. `pg.ValidateDBName` пропускает только строчные латинские буквы, цифры, `_`, `-`, `.`, требует
  совпадения с `databases.pattern` и отдельно отвергает обход каталогов (`../../etc/passwd`).
- Шаблон обслуживаемых баз обязан быть заякорен (`^…$`): незаякоренный отвергается при проверке конфига
  и не проходит в argv. Иначе совпадение нашлось бы в середине имени, и «своей» стала бы чужая база —
  а при восстановлении сервис очищает базу (`--clean --if-exists`).
- Пароли не хранятся: сервис работает через peer-аутентификацию и `sudo -n -u <владелец кластера>`,
  а контейнерный режим (0.3.0) — через `PGPASSFILE` с правами 0600. Пароль веб-пользователя хранится
  только bcrypt-хэшем: `sqlbrc hash-password` читает пароль из stdin (в аргументах командной строки
  его нет) и отвергает пароль длиннее 72 байт — bcrypt учитывает только первые 72 байта, и длинный
  пароль молча превращался бы в свой префикс.
- Правило sudoers перечисляет утилиты поимённо: `pg_dump`, `pg_restore`, `psql`, `pg_isready`.
  Правило вида `postgres ALL` сервису не нужно и расширяет его права.
- `storage.dir` — отдельный каталог сервиса: политика хранения удаляет старые дампы, поэтому рядом не должно
  быть чужих файлов. Файлы бэкапов создаются с правами 0640 (их читает пользователь кластера),
  а журнал задач в `storage.state_dir` — 0600: в нём имена баз и команды, но нет паролей.
- Перед восстановлением сверяется контрольная сумма архива: битый файл отвергается до первой команды,
  меняющей базу. Сбой записи метаданных не отменяет готовый архив (в списке он помечен «без метаданных»):
  восстановление из него возможно, а политика хранения считает его обычным бэкапом — время берётся из имени файла.
- `doctor` проверяет чтение архива пользователем кластера: отказы AppArmor не видны по правам каталога,
  а всплывают только при восстановлении.
- Веб-интерфейс: встроенные пользователи с bcrypt-хэшами (`auth.users`), токены API в отдельном
  файле (`auth.token_file`, права 0600), время жизни сессии, задержка между попытками входа и их
  предел; `server.read_only` запрещает изменяющие операции в CLI, в интерфейсе и в API одинаково.
- Файл токенов читается при старте: если он задан, а прочитать его нельзя, сервис не запускается —
  иначе API молча остался бы без доступа, и это выяснилось бы на первом запросе клиента.

## Как устроен каталог бэкапов

```
/var/backups/sqlbrc/
  fse-1234/
    20260921T020000Z.dump          архив pg_dump --format custom
    20260921T020000Z.json          метаданные: sha256, размер, формат, сжатие, версия сервера, задача
    20260921T030000Z-pre-restore.dump
    20260921T030000Z-pre-restore.json
  fssd-7/
    ...
/var/lib/sqlbrc/jobs.jsonl         журнал задач (0600): по две строки на задачу
```

Имя файла — метка времени в UTC: бэкап опознаётся по имени даже если файл метаданных потерян.
Незавершённая запись остаётся файлом `.dump.part` и не считается бэкапом: имя архива файл получает
одним переименованием после успешного дампа.

В `deploy/` лежат образцы, а не готовая конфигурация сервера: файл конфига, юниты systemd
(`sqlbrc.service`, `sqlbrc-backup.service` с таймером), правила межсетевого экрана
(`nftables/sqlbrc.nft`) и расписание бэкапов для систем без systemd (`cron.d/sqlbrc`).

## Ограничения

- **Логический бэкап, а не PITR.** `pg_dump --format custom --compress 6`: восстановление возможно только на
  момент снятия дампа. Непрерывного архивирования WAL и инкрементальных бэкапов нет.
- **Один сервер рядом с PostgreSQL.** Подключение идёт через локальный сокет: PostgreSQL и каталог
  бэкапов лежат на одной машине. В контейнере используется режим `postgres.mode: tcp`: сервис
  подключается к серверу по сети, а бэкапы живут в томе контейнера.
- **Расписание бэкапов настраивается отдельно.** В поставку входят таймер systemd
  (`deploy/systemd/sqlbrc-backup.timer`, ежедневный `backup --all`) и файл для cron
  (`deploy/cron.d/sqlbrc`); `doctor` предупреждает, если у обслуживаемых баз нет свежих бэкапов.
- **Одновременные операции по одной базе ограничены только внутри сервиса.** `jobs.max_per_db` не даёт
  запустить два дампа или восстановления одной базы через `sqlbrc`, но не мешает посторонним
  подключениям: перед восстановлением активные сессии завершаются (`databases.terminate_on_restore`).
- **Восстановление — это разворот базы целиком.** Отдельную таблицу или строку из дампа вернуть нельзя:
  база очищается (`--clean --if-exists`) и разворачивается заново (флаг `--no-clean` оставляет объекты,
  которых нет в дампе).
- **Восстановление в отсутствующую базу создаёт её с локалью по умолчанию** (`template0`), а клонирование
  берёт локаль источника. Если стенду нужна конкретная локаль, создайте базу заранее.
- **Сервис трогает только «свои» базы.** Имя должно совпадать с `databases.pattern` и не попадать в
  `databases.protected`, а сам шаблон обязан быть заякорен (`^…$`). Шаблон по умолчанию описывает
  строчные имена вида `<префикс>-<номер>`: `fse-1234`, `dops-fix-42` (префикс может состоять из
  нескольких сегментов через дефис), при этом номер в конце обязателен. Имя без номера в конце,
  с подчёркиванием или в верхнем регистре под шаблон не подходит — для таких стендов нужен свой
  `databases.pattern`.
- **Linux.** Проверки каталогов, прав, локалей, AppArmor и юнита systemd рассчитаны на Debian и подобные
  системы: на другой платформе `doctor` честно сообщит, что проверить не удалось.
- **Вход — по логину и паролю.** Интеграции с Keycloak/OIDC нет; TLS либо настраивается в сервисе
  (`server.tls`), либо подразумевает reverse-proxy (`sqlbrc serve --listen 127.0.0.1:8088`).
  Сессии живут в памяти процесса: перезапуск сервиса завершает вход, а отозвать одну сессию
  по имени нельзя — списка сессий на диске нет.
- **Политика хранения удаляет файлы** в `storage.dir`: каталог должен принадлежать сервису целиком.

## Разработка

| Команда | Что делает |
| --- | --- |
| `make` (`make all`) | обычная локальная проверка: `fmt`, `vet`, `test`, `build` |
| `make build` | собирает `bin/sqlbrc` с версией, коммитом и датой сборки (`make build VERSION=0.1.0` переопределяет версию) |
| `make version` | собирает бинарь и печатает `sqlbrc --version` |
| `make test` | `go test ./... -count=1` |
| `make vet` | `go vet ./...` |
| `make fmt` | `gofmt -l -w cmd internal` (а `make fmt-check` только показывает файлы) |
| `make lint` | `golangci-lint run ./...` с правилами из `.golangci.yml` |
| `make tidy` | `go mod tidy` |
| `make clean` | `go clean` и удаление `bin/` |

Тесты живут рядом с кодом (`*_test.go` в том же пакете), данные — в `testdata/`. Внешние процессы
(PostgreSQL, `sudo`) в тестах не запускаются: зависимости подменяются через интерфейсы, поэтому проверки
идут без сервера и на любой платформе разработки. Отдельные цели `cover` и `fuzz` в `Makefile` не
описываются, потому что они не нужны в CI: покрытие считает `go test -coverprofile`, fuzz-цели запускаются
как `go test -fuzz=Fuzz… ./internal/config`.
